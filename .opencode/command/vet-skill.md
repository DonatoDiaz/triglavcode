---
description: Vetting сторонних скиллов/плагинов перед установкой (security pipeline: audit → vault → sandbox)
---

Проведи аудит безопасности стороннего скилла/плагина перед его установкой и использованием, помести проверенную копию в vault и при `review`-вердикте выполни в песочнице.

## Вход

Цель — путь к SKILL.md, plugin-пакету, скрипту или репозиторию для проверки. Если цель не указана — спроси.

## Конвейер (аналог Hermes: ingest → audit → vault → sandbox)

1. **Сбор (ingest)** — загрузи/прочитай целиком: SKILL.md, команды, скрипты, package.json, AGENTS.md в папке скилла.

2. **Статический анализ (audit)**:
   - Обфускация (base64-блоки, свёрнутые имена, `eval`/`Function`/`vm.runInNewContext`)
   - Сетевые вызовы: куда уходят данные, есть ли загрузка и запуск удалённого кода
   - `exec`/`spawn`/`child_process`: какие команды и откуда берутся их аргументы
   - Доступ к файлам за пределами рабочей папки, к `~/.ssh`, `.env`, секретам, ключам
   - Чтение/передача переменных окружения наружу
   - Запуск при установке скрытых postinstall-скриптов
   - Подмена инструментов (tool names, мимикрия под систему)

3. **Vault** — только для чистой копии:
   - Скопируй ревизию целиком в `.opencode/vault/skills/<name>/` (вне рабочей папки проекта, нетронутая копия проверенного состояния).
   - Запиши манифест `.opencode/vault/skills/<name>/MANIFEST.json`: `{ name, source, date, hash, verdict }` — хэш содержимого для проверки позже.
   - Впредь устанавливай скилл только из vault-копии, а не по исходной ссылке (защита от подмены источника после проверки).

4. **Sandbox** (только для вердикта `review`):
   - Выполняй скилл в изолированной песочнице, а не в рабочей папке: временный каталог (`/tmp/...`), пустой git-репозиторий, без доступа к реальным ключам/секретам (подставь фиктивные), без запуска postinstall.
   - Ограничь сеть и файловую систему (если доступно — container/sandbox-раннер; иначе минимум: отдельная папка + фиктивные env + запрет на запись вне `/tmp`).
   - Следи, куда скилл пишет и обращается. После прогона проверь, что изменений в рабочей папке нет (`git status` чист).
   - Только после успешного sandbox-прогона предлагай перенос в рабочую папку.

5. **Trust-tier вердикт** (один из):
   - `trusted` — нет подозрительных паттернов, только локальные операции → vault, можно ставить из vault-копии
   - `review` — есть необычные сетевые/exec/файловые операции, но явные и объяснимые → vault + sandbox-прогон перед использованием
   - `quarantine` — обфускация или скрытая эксфильтрация; **не устанавливать**, не помещать в vault

6. **Отчёт**: что делает; подозрительные находки со ссылками на строки; вердикт; где vault-копия; результат sandbox-прогона; рекомендация (установить / в sandbox / отказаться).

Никогда не пиши вердикт `trusted`, если не прочитал весь код сами. Не запускай испытуемый код во время audit-фазы — только после vault, в sandbox.
